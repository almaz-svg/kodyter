# Резервное копирование и восстановление

Основные рабочие данные Docker-версии находятся в PostgreSQL. Изображения сайта входят в сборку, а том `media_data` зарезервирован для файлов. Скрипты сохраняют базу в формате pg_dump custom, содержимое media и SHA-256 каждой копии. Дамп переносится через `docker cp`, поэтому PowerShell не преобразует его бинарное содержимое.

## Создать копию

Из корня проекта при работающих контейнерах:

```powershell
./scripts/backup.ps1
```

Результат: `backups/<дата-время>/database.dump`, `media.tar.gz`, `backup.json`. Можно выбрать новый каталог через `-Destination`. Существующий каталог не перезаписывается. Пароли не включаются в файл описания копии.

pg_dump создаёт согласованный снимок базы; media копируется отдельно. Если в будущем приложение будет изменять загруженные файлы, на время полной копии остановите запись: `docker compose stop backend`, выполните backup, затем `docker compose start backend`. Витрина в этот промежуток не сможет работать с API.

Храните копию вне сервера в месте с ограниченным доступом и шифрованием. Отдельно сохраните конфигурацию `.env`, секреты SMTP, доступ к DNS и версию исходного кода. Не публикуйте их в Git. Периодичность и срок хранения определяет владелец; для начала можно организовать ежедневную копию и проверяемую копию перед каждым обновлением. Сам скрипт не создаёт расписание.

## Восстановить

Восстановление заменяет содержимое текущей базы. Сначала сделайте свежую копию и убедитесь, что выбран правильный Docker-проект. Для проверки восстановления предпочтительна отдельная тестовая среда с той же версией PostgreSQL.

```powershell
./scripts/restore.ps1 -BackupDirectory "./backups/20261015-120000-example" -ConfirmRestore
```

Замените путь на существующий каталог. Скрипт сверяет контрольные суммы, проверяет читаемость дампа и пути архива, останавливает backend, восстанавливает базу одной транзакцией, возвращает media с защитным фильтром Python tarfile и запускает backend. Если восстановление не завершилось, backend остаётся остановленным, чтобы не принимать новые заказы до проверки. Прочитайте ошибку, устраните причину и только затем выполните `docker compose start backend`.

Файлы media, присутствующие в копии, восстанавливаются с заменой одноимённых. Дополнительные файлы, созданные после копии, остаются в томе: скрипт не удаляет их автоматически. Для полного возврата файлового тома к определённому состоянию используйте отдельный новый том в тестовой среде.

После восстановления проверьте `/api/health/`, вход каждой роли, каталог, один существующий заказ, историю статусов и тестовое оформление. Сравните ожидаемые количества пользователей, товаров и заказов. Успешный код pg_restore сам по себе не заменяет эту проверку.

## Локальный PostgreSQL 18 без Docker

Текущая среда использует отдельный кластер `.secrets/postgres-data` на `127.0.0.1:55432`, базу `anasym`, роль `anasym_app`. Пароль лежит в `.secrets/postgres-app-password.txt`. Для создания копии используйте `pg_dump` той же или более новой основной версии, чем сервер:

```powershell
$pgBin = 'C:/Program Files/PostgreSQL/18/bin'
$oldPgPassword = $env:PGPASSWORD
try {
    $env:PGPASSWORD = [IO.File]::ReadAllText((Join-Path $PWD '.secrets/postgres-app-password.txt')).Trim()
    New-Item -ItemType Directory -Force -Path backups | Out-Null
    $dumpPath = Join-Path $PWD ('backups/local-' + (Get-Date -Format 'yyyyMMdd-HHmmss') + '.dump')
    & "$pgBin/pg_dump.exe" -h 127.0.0.1 -p 55432 -U anasym_app -d anasym -Fc --no-owner --no-acl -f $dumpPath
    if ($LASTEXITCODE -ne 0) { throw 'pg_dump failed' }
    Get-FileHash -LiteralPath $dumpPath -Algorithm SHA256
} finally { $env:PGPASSWORD = $oldPgPassword }
```

Пароль временно передаётся через окружение процесса и не включается в аргументы команды или вывод. Сохраните путь к дампу и его контрольную сумму.

Для безопасной проверки восстановления создайте отдельную базу. В том же блоке `try/finally` с временным `PGPASSWORD` выполните команды ниже, заменив путь копии. Имя проверочной базы должно быть новым:

```powershell
& "$pgBin/createdb.exe" -h 127.0.0.1 -p 55432 -U anasym_app anasym_restore_check
if ($LASTEXITCODE -ne 0) { throw 'Could not create restore test database' }
& "$pgBin/pg_restore.exe" -h 127.0.0.1 -p 55432 -U anasym_app -d anasym_restore_check --no-owner --no-acl --exit-on-error --single-transaction 'backups/your-copy.dump'
if ($LASTEXITCODE -ne 0) { throw 'pg_restore failed' }
```

Для восстановления основной базы остановите приложение, убедитесь, что изолированный PostgreSQL продолжает работать, сделайте свежую копию и используйте `pg_restore -d anasym --clean --if-exists` вместе с остальными флагами выше. Это заменяет данные. Учтите, что `scripts/stop.ps1` останавливает и PostgreSQL, если запускал его самостоятельно; после такого завершения кластер потребуется отдельно запустить до восстановления. Не восстанавливайте данные при работающем backend.

## Локальная SQLite-среда

Этот режим включается только флагом `-UseSqlite` и не является заменой PostgreSQL-приёмки. Остановите сервер через `scripts/stop.ps1` и скопируйте `backend/db.sqlite3` в защищённое место. Для возврата сохраните текущий файл отдельно и замените его нужной копией при остановленном сервере. Docker-скрипты backup/restore к SQLite не применяются.

## Ограничения проверки в текущей среде

Синтаксис скриптов и конфигурация Compose проверены. API, сохранность после перезапуска и полный цикл pg_dump → pg_restore проверены на локальном PostgreSQL. Docker engine недоступен, поэтому контейнерные скрипты копирования и восстановления ещё не проверены выполнением; перед использованием контейнерной копии как единственной выполните пробное восстановление.
